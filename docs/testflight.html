TestFlight runbook

How to get a native iOS build of this idea onto your phone through TestFlight. This is the path. It is not a shipped app yet. The website prototypes stay as references. Do not wrap them in a web view and call that the product.

What the iOS app is

SwiftUIThe conversation. One thread is enough for the first flight.
→
App sandboxMessages in a local database inside the app container. Not iCloud. Not a server.
→
On-device runtimeA small instruct model run by a native engine (MLX or llama.cpp on the GPU). The text never leaves the process.

Ship a small quant in the app, or have the first launch import a weights file the person already has. Do not call OpenAI, Anthropic, xAI, or Ollama-on-a-Mac from the phone. A model that only works while a desktop is on is not the TestFlight idea.

What you need before Xcode

  1. A Mac with a current Xcode.
  2. An Apple Developer Program membership for the Apple ID that will upload the build. TestFlight requires that membership. A free Apple ID can run on your own phone from Xcode, but it cannot upload to TestFlight.
  3. A bundle identifier you own, for example com.mikail.privatechat.
  4. A decision on the first model: something in the 1B class, quantized, so the upload is a normal archive and the phone can answer without a desktop. Larger models can wait until the loop (type, reply, relaunch, history still there) is proven.

The build, in order

  1. In Xcode, create an iOS App (SwiftUI, Swift). Set the team and the bundle id. Turn off iCloud, push, and any analytics capability.
  2. Store messages in the app container (SwiftData or a small SQLite file). Write the user line before inference. Write the reply after. On failure, keep the user line and show an error.
  3. Add the on-device engine and the weights. The engine loads from the bundle or from a file the user imported. There is no chat URL in the app.
  4. Run it on a simulator, then on your phone with a cable, before any upload. Check three things: a reply appears, the reply is still there after you kill the app, and the device shows no connection to a chat host while you send (Xcode’s network instrument, or a packet capture, while the phone is off Wi-Fi except for nothing).
  5. In App Store Connect, create the app with the same bundle id. You do not submit it for App Store review.
  6. In Xcode, archive the app (Any iOS Device), then Distribute → TestFlight / App Store Connect. Wait until the build finishes processing.
  7. Internal testing: add your Apple ID on the team. Internal testers can install without a beta review. External testing needs a short beta review and a privacy note. Start internal.
  8. Install TestFlight on the phone, accept the build, and repeat the same three checks on the installed build, not only the Xcode-run one.

What to tell TestFlight’s privacy questions

The app does not collect the conversation. Say that messages and the model stay on device, and that the only network use you know of is Apple’s own TestFlight install and crash reporting if you left crash reporting on. Turn crash reporting off for this flight if you want the claim to stay simple. Do not claim the transcript is encrypted at rest unless you have actually added that. The app sandbox is not the same as encryption.

Leave out of the first flight

  • Accounts, sync, share extensions, and iCloud backup of the transcript.
  • A model picker, voice, and images.
  • System One (Laya and the others). Add that only after a reply can be produced with no network.
  • The Kiln and Still web pages. They explain the wall. They are not the iOS binary.

When you want this built in a repo rather than described, the first milestone is the three checks on a cable-installed build. TestFlight is the step after that, not before.
